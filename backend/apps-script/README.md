# Bunfirvil 인증·회원 운영 (회원코드 개정 1)

이 코드는 **같은 비공개 스프레드시트 안의 가입요청 / 인증명단 두 탭**을 사용합니다. 웹사이트는 명단을 내려받지 않습니다. 일반 회원 권한에는 동·타입·닉네임과 개인 회원코드가, 공유 열람의 회원 권한에는 보는 사람의 동·닉네임과 개인 회원코드가 필요합니다. 층·호수는 전송하지 않습니다. 코드가 없는 방문자의 공개 입장은 그대로 유지합니다.

## 기존 사이트 업데이트 순서 — 먼저 Google, 다음 Pages

**Google 웹앱부터 새 버전으로 배포한 후 GitHub Pages를 갱신하세요.** 새 프런트엔드는 회원코드 확인 표식 없는 구형 회원 인증 응답을 거부합니다. 운영자는 기존 `authRevision: 2`와 별도 운영자 코드 방식을 유지합니다. 회원 성공 응답에는 `memberCodeVerified: true`, `memberCodeRevision: 1`이 추가됩니다.

1. 기존 스프레드시트를 복사해 별도 백업합니다. 편집 권한은 신뢰하는 운영자에게만 줍니다.
2. 프로젝트의 [backend/apps-script/Code.gs](Code.gs)는 에이전트가 작성·검증하는 **원본 견본**입니다. 이 파일을 수정하거나 GitHub에 올려도 Google 쪽 스크립트가 자동으로 바뀌지는 않습니다. 인증 Sheet에서 **확장 프로그램 → Apps Script → Code.gs**를 열고 견본 전체로 교체한 뒤 저장합니다. Sheet에서 직접 변경한 경우에는 다음 개정 때 덮어쓰지 않도록 견본에도 같은 변경을 반영합니다.
3. 함수 선택에서 **setupVerificationSheet**를 한 번 실행하고 권한을 승인합니다.
   - 기존 인증명단 A:D와 회원 데이터를 유지합니다.
   - E:G에 `회원코드 해시 / 회원코드 발급일 / 회원코드 폐기일`을 추가합니다. 세 열의 헤더와 데이터가 모두 비어 있을 때만 초기화하며, 다른 내용이 있으면 덮어쓰지 않고 중단합니다.
   - 가입요청 탭, 심사 드롭다운, 설치형 편집 트리거를 준비합니다.
   - 기존 다른 Script Properties는 지우지 않습니다.
   - 헤더가 다르면 덮어쓰지 않고 중단합니다. 구형 동/호수 명단은 백업 후 B열을 타입으로 직접 정리하세요.
4. 운영자 코드를 아직 설정하지 않았다면 **configureOperatorCode**를 실행합니다. 기존 운영자 코드는 설치 과정에서 지우거나 변경하지 않습니다. Sheet 입력창에 비밀번호 관리자로 만든 **16~128자의 무작위 코드**를 넣습니다.
   - 공개 닉네임과 다른 값이어야 합니다. 실제 코드를 채팅·GitHub·공개 설정 파일로 보내지 마세요.
   - 코드의 SHA-256 해시만 Script Properties에 저장합니다.
   - 이 프로젝트의 Sheet 운영자들은 같은 별도 코드를 사용합니다. Google 사용자별 로그인이 필요하면 별도 인증 시스템이 필요합니다.
   - 이 운영자 설정용 기본 프롬프트는 글자를 가리지 않습니다. 다른 사람에게 화면을 공유하지 않는 상태에서 입력하세요.
5. Sheet를 새로고침하면 **분퍼빌 회원 관리** 메뉴가 나타납니다.
   - 기존 요청이 있다면 **기존 요청 분리 (백업 후 이동)**를 실행합니다.
   - 확인창 승인 후 인증백업-시각 탭을 만들고 요청 행만 가입요청으로 옮깁니다.
   - 인증됨·운영자·중지 행은 유지합니다. 요청 목적지 기록 후 원본 요청 행을 제거하므로 중간 실패 시 다시 실행할 수 있습니다.
6. 아래 **회원 코드 발급/재발급** 절차로 임시 회원과 기존 회원의 코드를 준비해 각각 1:1로 전달합니다. 승인만으로 코드는 발급되지 않습니다.
7. Google 웹앱을 배포합니다. 코드 저장이나 함수 실행만으로 기존 웹앱의 배포 버전이 자동 갱신되지는 않습니다.
   - **기존 배포 수정 권장:** **배포 → 배포 관리**에서 현재 웹앱의 수정 아이콘을 누르고 **버전 → 새 버전 → 배포**를 선택합니다. 대개 기존 웹 URL을 그대로 사용합니다.
   - **첫 배포 또는 새 배포가 필요한 경우:** **배포 → 새 배포 → 유형 선택 → 웹 앱**을 선택하고 배포합니다. 새 배포는 기존과 다른 웹 URL을 만들 수 있습니다.
   - 두 경우 모두 실행 사용자 **나**, 액세스 권한 **모든 사용자**를 확인합니다. Google 계정 승인 화면이 나오면 권한을 검토한 뒤 승인합니다.
8. 완료 창 또는 **배포 관리**의 웹앱 상세에서 **웹 앱 URL**을 복사합니다. 끝이 `/exec`인 전체 HTTPS 주소가 필요하며, **배포 ID는 주소가 아닙니다**. 편집기 URL·스프레드시트 URL·`/dev` 주소도 사용하지 않습니다.
9. 에이전트에게 웹 앱 URL만 전달하거나 프로젝트의 `public/config/household-verification.v1.json`을 엽니다. 주소가 바뀌었다면 JSON의 `endpoint` 문자열만 `/exec` URL 전체로 교체하고, 큰따옴표와 나머지 설정을 유지해 저장합니다. 기존 배포 수정으로 URL이 그대로라면 이 파일을 바꿀 필요가 없습니다. 웹 앱 URL은 공개 설정이므로 공유 가능하지만 **Spreadsheet ID·회원 명단·개인코드·운영자 코드는 전달하지 않습니다**.
10. Google 웹앱의 새 응답이 정상인지 확인합니다. 임시 회원 하나로 코드 없음/오류/정상 일반 인증, 다른 타입 공유 열람, 재발급·폐기, 운영자 코드, 등록→승인→코드 발급을 확인합니다. 테스트가 끝나면 임시 코드를 폐기하고 행을 제거합니다. 실제 회원의 코드는 테스트를 위해 채팅·저장소에 적지 않습니다.
11. 프런트 변경이나 URL 설정 변경을 커밋하기 전 프로젝트 루트에서 관련 검사와 빌드를 실행합니다. 필요하면 에이전트가 수행합니다.

    ```powershell
    npm run test:unit -- src/game/apps-script-contract.test.ts src/game/household-verification.test.ts
    npm run build
    npm run verify:dist
    ```

12. 변경분을 `main`에 커밋·푸시하고 GitHub Actions의 Pages 배포가 **성공**할 때까지 확인합니다. 공개 사이트의 설정 파일이 선택한 `/exec` URL과 일치하는지, 공개 입장 및 임시 회원 인증이 예상대로 동작하는지 확인합니다. 회원코드 표식 없는 구형 일반 회원 세션은 한 번 다시 인증합니다. 기존 정상 운영자 세션과 공개 입장·옵션 저장은 변경하지 않습니다.

배포 후 문제가 생기면 이전 웹앱 배포를 임의로 삭제하거나 새 URL을 추측하지 말고, **배포 관리의 선택된 웹 URL → JSON `endpoint` → Pages 배포 커밋**이 같은 버전을 가리키는지 확인하세요. 임시 회원 인증과 공개 입장은 별도로 점검합니다.

## 탭과 상태

| 탭 | 열 | 용도 |
| --- | --- | --- |
| 인증명단 A:D | 동 / 타입 / 닉네임 / 상태 | 인증됨·운영자·중지 회원만 관리 |
| 인증명단 E:G | 회원코드 해시 / 회원코드 발급일 / 회원코드 폐기일 | 정상 회원의 코드 관리 메타데이터. 원문 저장 금지 |
| 가입요청 | 요청ID / 요청일시 / 동 / 타입 / 닉네임 / 심사결정 / 처리결과 / 처리일시 | 대기·승인·반려 이력 |

가입요청 A:B·G:H와 인증명단 E:G는 자동 기록입니다. 필요하면 숨기고 요청 C:F·회원 A:D를 중심으로 보세요. 요청 원문·자동 열과 인증명단 권한/코드 열은 시트 보호 기능으로 제한하는 것을 권장합니다. Sheet를 공개하거나 전체 회원 명단을 공유하지 마세요. 드롭다운은 인증 보안 장치가 아닙니다.

E:F:G는 운영자가 코드를 입력하는 칸이 아닙니다. **발급·재발급 시 E 해시와 F 발급일을 기록하고 G 폐기일을 비웁니다. 폐기 시 E 해시를 지우고 F 발급일은 유지하며 G 폐기일을 기록합니다.** 날짜는 UTC 기준 ISO 문자열(`Z`)로 저장됩니다. 발급 전이거나 폐기 후라면 E열이 비어 있을 수 있습니다.

### 일상 승인

1. 가입요청에서 동·타입·닉네임을 확인합니다.
2. F열 심사결정을 **승인**으로 바꿉니다.
3. G열에 **승인 완료**가 표시되는지 확인합니다. 인증명단에는 인증됨 회원이 중복 없이 추가됩니다.
4. 실패 표시가 나오면 원문/기존 회원 상태를 정리하고 **미처리 승인 / 반려 재처리**를 실행합니다.
5. 실제 회원임을 별도로 확인한 뒤 아래 메뉴로 개인 코드를 발급해 1:1로 전달합니다. 사용자는 코드와 함께 인증 확인을 다시 누릅니다.

승인 성공 후에는 요청 행을 삭제하지 말고 필터로 감춰 이력을 보관하세요. 승인 완료 행의 결정을 바꿔도 회원을 삭제하지 않으며 승인으로 복원됩니다. 회원을 중지하려면 인증명단의 상태를 중지로 바꿉니다.

반려된 요청은 재신청해도 자동 승인/대기로 바뀌지 않습니다. 재심사할 때 운영자가 F열을 대기 또는 승인으로 바꾸세요. 승인으로 운영자를 새로 만들거나 중지 회원을 복구할 수는 없습니다.

### 회원 코드 발급/재발급·폐기

1. `인증명단`에서 대상 **인증됨 회원 한 행**을 선택합니다. 헤더·여러 행·가입요청·운영자·중지 행에서는 발급하거나 폐기할 수 없습니다.
2. **분퍼빌 회원 관리 → 선택 회원 코드 발급/재발급**을 누릅니다.
3. 모달의 대상 동·타입·닉네임을 확인하고 **새 코드 발급**을 누릅니다.
   - Sheet 모달 브라우저의 `crypto.getRandomValues`로 32바이트를 생성해 43자 base64url 코드로 만듭니다. `Math.random`이나 UUID로 대체하지 않습니다. [Web Crypto 난수 생성](https://developer.mozilla.org/en-US/docs/Web/API/Crypto/getRandomValues)
   - 안전한 자동 생성이 없는 환경에서는 오류를 표시합니다. **비밀번호 관리자 코드 사용**에서 관리자 도구로 만든, 공백 없는 영문·숫자·기호 16~128자 무작위 코드를 대신 입력할 수 있습니다. 닉네임·전화번호·짧은 PIN을 사용하거나 다른 회원 코드를 재사용하지 마세요.
4. 서버가 선택행·회원 정보·인증됨 상태를 다시 확인하고 해시 저장에 성공해야 원문이 한 번 표시됩니다. **코드 복사**로 복사하고, 실제 회원인지 별도 확인한 1:1 연락으로 전달하세요. 자동 복사가 막히면 선택된 코드를 직접 복사합니다.
5. 모달을 닫으면 원문을 다시 조회할 수 없습니다. 원문은 시트·Script/User Properties·로그·공개 API 응답에 보관하지 않습니다. 분실했다면 같은 메뉴로 새 코드를 발급하세요. 저장 확인 실패 시에는 코드를 전달하지 말고 창을 닫아 다시 발급합니다.
6. 폐기는 같은 회원 행에서 **선택 회원 코드 폐기**를 누릅니다. E열 해시를 지우고 G열에 폐기일을 기록하며 회원 상태·동·타입·닉네임은 유지합니다. 인증됨 상태라도 코드가 없거나 폐기되었으면 새 회원 인증은 실패합니다.

발급 창은 5분 동안 유효하며, 창을 연 뒤 선택행·대상 정보·상태가 바뀌면 저장을 거절합니다. 발급은 Sheet의 바인딩된 메뉴/HTML Service 문맥에서만 허용하고 공개 `doPost`에 발급·재발급·폐기 action을 제공하지 않습니다. 비동기 통신은 [Google HTML Service](https://developers.google.com/apps-script/guides/html/communication)를 사용합니다.

회원 해시는 정규화한 동·타입·닉네임과 코드를 결합한 SHA-256입니다. A:C를 다른 회원 정보로 수정하거나 해시를 다른 행에 복사해도 기존 코드가 그 회원을 인증하지 못합니다. 동·타입·닉네임이 실제로 바뀌면 재발급하세요. `55a`/`55A`, 앞뒤 공백처럼 정규화 결과가 같은 값은 동일하게 인식합니다. 현재 저장된 본인·다른 회원의 코드 재사용도 발급 시 거절합니다.

재발급은 기존 코드를 다음 인증부터 즉시 무효화합니다. **이미 열린 탭은 서버에 매번 재확인하지 않으므로 즉시 로그아웃되지 않을 수 있습니다.** 폐기·중지도 같습니다. 즉시 세션 차단이 필요한 원격 관리 기능은 별도의 서버 세션 검증이 필요합니다.

### 운영자

- 인증명단 상태가 운영자이며 **별도 코드가 일치**해야 모든 동·타입에 접근합니다.
- 닉네임만 아는 사람에게 운영자 역할을 주지 않습니다. 등록 요청도 운영자 행을 새로 만들지 않습니다.
- 코드는 비밀번호 입력으로 POST 전송하며 브라우저 저장소·공유 URL에 넣지 않습니다.
- 코드 미설정은 실패 처리합니다. 잘못된 코드 6회 후에는 해당 닉네임의 추가 시도를 약 10분 제한합니다.
- 이는 단순한 추가 확인이며 정적 사이트 UI 권한입니다. 브라우저의 역할 값을 개발자 도구로 조작하는 것까지 막는 서버 접근통제는 아닙니다. 민감한 데이터·원격 관리 기능을 붙일 때는 Google 로그인 등 서버 검증 방식이 필요합니다.

### 공유와 개인 놀이터

- 개인 놀이터 회원 인증: 동 + 타입 + 닉네임 + 개인 회원코드 + 인증됨.
- 공유 놀이터 회원 인증: **보는 사람**의 동 + 닉네임 + 개인 회원코드로 확인합니다. 코드 해시는 실제 회원 행의 타입과 결합해 검사하며 공유자의 타입은 인증 조건이 아닙니다.
- 공유 인증으로 얻은 일반 회원 세션은 공유 열람용입니다. 개인 놀이터에 진입하려면 본인 세대를 선택해 다시 인증합니다.
- 공유 화면은 운영자에게도 읽기 전용입니다.
- 공유 화면에서 새 등록을 받을 때 공유자의 타입으로 잘못 등록하지 않도록 본인 세대 선택 화면으로 안내합니다.
- 닉네임만 알아서는 회원 권한을 얻을 수 없습니다. 다만 본인이 코드를 다른 사람에게 전달하면 대리 인증이 가능하므로 코드를 공개하지 마세요.
- 공개 권한으로 개인·공유 놀이터를 보는 기존 흐름은 유지합니다. 코드는 회원 기능을 위한 추가 확인이며 비공개 자산을 보호하는 서버 접근통제는 아닙니다.
- 코드 원문은 비밀번호 입력으로 JSON POST에만 넣고 sessionStorage·localStorage·공유 URL에 저장하지 않습니다. 기존 승인 회원이 등록요청 버튼을 다시 눌러도 코드 확인 없이 회원 권한을 주지 않습니다.

## 한도·복구

- 회원은 전체 행을 읽습니다. 이전의 5,000행 이후 회원 누락은 없습니다.
- 요청은 최대 5,000행 보관, 대기 최대 300건입니다. 한도 도달 시 새 접수를 거부하고 안내합니다.
- 같은 동·타입·닉네임의 반복 신청은 기존 행을 사용합니다. 같은 닉네임의 새 요청은 1분 간격으로 제한합니다.
- CacheService 제한은 남용 완화용이며 강한 봇 차단은 아닙니다. 심한 트래픽에는 별도 서비스가 필요합니다.
- 회원 코드 실패는 정규화 동·타입·닉네임의 해시 키로 6회 후 약 10분 제한합니다. 빈 입력 안내는 세지 않지만 잘못된 짧은 코드 등 비어 있지 않은 실패는 포함합니다. 일반/공유 경로를 각각 제한하며 캐시 읽기·쓰기에는 ScriptLock을 사용합니다. 캐시는 만료 전 제거될 수도 있으므로 영구적인 보안 잠금으로 보지 않습니다. [CacheService 보관 특성](https://developers.google.com/apps-script/reference/cache/cache)
- = 등으로 시작하는 닉네임은 수식이 아닌 텍스트로 저장합니다.
- 상태 중지는 새 인증부터 반영됩니다. 이미 열린 탭은 탭 종료/세대 다시 선택 전까지 인증이 남을 수 있습니다.
- 설치형 트리거는 설치 계정 권한으로 동작합니다. 스크립트/API로 값을 바꾸면 편집 트리거가 실행되지 않으므로 일괄 작업 뒤 재처리 메뉴를 실행하세요.
- 자동 백업 탭은 직접 삭제하지 않는 한 복구용으로 남습니다. 실패한 이동은 백업과 목적지 요청 행을 확인한 후 재실행하세요.
