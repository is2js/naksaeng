# 인증·회원 운영 개정판

이 코드는 **같은 비공개 스프레드시트 안의 가입요청 / 인증명단 두 탭**을 사용합니다. 웹사이트는 명단을 내려받지 않습니다. 일반 회원 인증은 동·타입·닉네임과 **회원 개인코드**를, 공유 열람의 회원 인증은 보는 사람의 동·닉네임과 **회원 개인코드**를 확인합니다. 층·호수는 전송하지 않습니다.

## 현재 운영 계약

- 사이트는 전체 공개입니다. 미등록 사용자도 동·세대·닉네임을 입력하면 공개 권한으로 입장하며, 가구 배치·평면 전환·변신은 정상 인증된 회원과 운영자에게만 제공합니다.
- 공개 권한은 프런트엔드 세션에만 기록합니다. Sheet에 공개 행이나 새 상태를 추가하지 않습니다. 개인코드가 없어도 공개 입장은 그대로 가능하지만, **회원 개인코드 도입에는 아래 순서의 Apps Script 새 버전 배포와 프런트엔드 갱신이 필요합니다.**
- 등록 대기·반려·중지·통신 오류는 회원 권한을 부여하지 않지만 공개 입장을 막지 않습니다. 중지는 회원 기능 중지이며 사이트 열람 차단 수단이 아닙니다.
- `가입요청`은 신청·승인·반려 이력을 남기는 접수 탭입니다.
- `인증명단`은 실제 인증 판정에 사용하는 회원 탭입니다. 상태는 `인증됨 / 운영자 / 중지`만 사용합니다.
- 일반 회원은 동·타입·닉네임과 개인코드가 일치해야 하며, 운영자는 고유 닉네임과 **기존 별도 운영자 코드**가 모두 맞아야 전역 접근합니다. 회원 개인코드와 운영자 코드는 서로 대체하지 않습니다.
- 공유 열람의 회원 인증은 보는 사람의 동·닉네임과 개인코드를 확인합니다. 인증 없이 공개 권한으로도 열람할 수 있으며, 인증을 통과해도 공유 놀이터는 읽기 전용입니다.
- Spreadsheet ID, 실제 회원 데이터, 회원·운영자 코드 원문과 해시는 저장소·공개 설정·로그에 넣지 않습니다. 코드는 브라우저 인증 세션이나 공유 링크에도 저장하지 않습니다.

## 기존 사이트 업데이트 순서 — 먼저 Google, 다음 Pages

새 프런트엔드는 일반 회원의 정상 응답에 `memberCodeVerified: true`와 `memberCodeRevision: 1`을 요구합니다. 기존 운영자 인증의 `authRevision: 2` 계약과 별도 코드는 유지합니다. **Google 웹앱부터 새 버전으로 배포한 후 GitHub Pages를 갱신하세요.** 구·신 버전이 섞이면 회원 기능은 인증되지 않을 수 있지만 공개 입장은 막지 않습니다.

### 먼저 이해할 두 파일과 두 주소

- 프로젝트의 `backend/apps-script/Code.gs`는 에이전트가 수정·검증하는 **소스 견본**입니다. 이 파일을 고치거나 GitHub에 올려도 Google에 자동 적용되지는 않습니다. 실제 인증 서버는 인증 Sheet의 **확장 프로그램 → Apps Script → Code.gs**에 붙여 넣고 웹앱으로 배포한 코드입니다. 아직 커밋하지 않은 변경은 GitHub의 기존 파일이 아니라 로컬 프로젝트 파일을 복사하세요.
- 프로젝트의 `public/config/household-verification.v1.json`은 사이트가 호출할 Google 웹앱 주소를 지정합니다. 이 파일을 로컬에서 저장한 것만으로 공개 사이트가 바뀌지는 않으며, GitHub Pages 빌드·배포까지 끝나야 적용됩니다.
- **Spreadsheet ID**는 시트의 주소에 들어가는 ID이고, **배포 ID**는 Apps Script 배포를 식별합니다. 둘 다 `endpoint`에 넣지 않습니다. 필요한 값은 **웹 앱 URL 전체**이며 `https://script.google.com/macros/s/…/exec` 형태입니다. `/dev`는 개발용이므로 공개 설정에 넣지 않습니다.

### 1. 소스 수정 및 Sheet 설치

1. 기존 스프레드시트를 복사해 별도 백업합니다. 편집 권한은 신뢰하는 운영자에게만 줍니다.
2. Sheet의 **확장 프로그램 → Apps Script**에서 [Code.gs 전체 보기](https://github.com/is2js/naksaeng/blob/main/backend/apps-script/Code.gs) 전체를 교체하고 저장합니다. 회원코드 발급 모달도 이 파일에 포함되므로 별도의 HTML 파일을 만들 필요는 없습니다.
3. 함수 선택에서 **setupVerificationSheet**를 한 번 실행하고 권한을 승인합니다.
   - 기존 인증명단 A:D와 회원 데이터를 유지합니다.
   - 인증명단 E:G가 모두 비어 있을 때만 **회원코드 해시 / 회원코드 발급일 / 회원코드 폐기일**을 추가합니다. 기존 코드 메타데이터는 유지하며, 다른 헤더가 있으면 임의로 덮어쓰지 않고 중단합니다.
   - 가입요청 탭, 심사 드롭다운, 설치형 편집 트리거를 준비합니다.
   - 기존 다른 Script Properties는 지우지 않습니다.
   - 헤더가 다르면 덮어쓰지 않고 중단합니다. 구형 동/호수 명단은 백업 후 B열을 타입으로 직접 정리하세요.
4. 운영자 코드를 처음 설정하거나 교체할 때만 Sheet 메뉴 **분퍼빌 회원 관리 → 운영자 인증코드 설정**을 실행합니다. 기존 코드는 그대로 유지할 수 있습니다. 모달의 **무작위 코드 생성**을 누르면 안전한 43자 코드가 입력칸에 자동 생성됩니다. 기존 코드를 교체한다는 안내를 확인한 뒤 **설정 및 저장**을 누르세요.
   - 공개 닉네임과 다른 값이어야 합니다. 실제 코드를 채팅·GitHub·공개 설정 파일로 보내지 마세요.
   - 코드의 SHA-256 해시만 Script Properties에 저장합니다.
   - 이 프로젝트의 Sheet 운영자들은 같은 별도 코드를 사용합니다. Google 사용자별 로그인이 필요하면 별도 인증 시스템이 필요합니다.
   - 저장 성공 후 **코드 복사**로 복사해 비밀번호 관리자에 보관하세요. 원문을 잃으면 다시 조회할 수 없으므로 재설정해야 합니다. 이미 열린 탭의 인증은 즉시 회수되지 않을 수 있습니다.
   - 입력은 기본적으로 가려지며 **코드 보기**로 확인할 수 있습니다. 생성에는 브라우저의 Web Crypto를 사용하고, 지원하지 않으면 자동 생성하지 않습니다. 이 경우 다른 브라우저나 비밀번호 관리자에서 만든 무작위 16~128자 코드를 직접 입력하세요. 화면 공유·주변 노출·스크린샷에 주의하세요.
   - Apps Script 편집기에서 실행할 때는 Sheet에 연결된 프로젝트인지 확인하고 `configureOperatorCode`를 실행할 수 있습니다. 초기 설치가 끝나야 하며, 실제 Sheet의 코드 변경 후에는 Sheet를 새로고침해 메뉴를 다시 여세요.
5. Sheet를 새로고침하면 **분퍼빌 회원 관리** 메뉴가 나타납니다.
   - 기존 요청이 있다면 **기존 요청 분리 (백업 후 이동)**를 실행합니다.
   - 확인창 승인 후 인증백업-시각 탭을 만들고 요청 행만 가입요청으로 옮깁니다.
   - 인증됨·운영자·중지 행은 유지합니다. 요청 목적지 기록 후 원본 요청 행을 제거하므로 중간 실패 시 다시 실행할 수 있습니다.
### 2. Google 웹앱 배포와 URL 확인

6. 실제 웹앱에 새 코드를 적용합니다. 두 방법 중 하나를 사용합니다.
   - **기존 주소를 유지하려면 권장:** **배포 → 배포 관리**에서 현재 사이트가 사용하는 활성 웹앱을 선택하고 **수정 → 버전: 새 버전 → 배포**를 누릅니다. 새 버전을 기존 배포에 연결하는 방식이므로 URL과 배포 ID가 유지됩니다. [Google 배포 관리 안내](https://developers.google.com/apps-script/concepts/deployments)
   - **별도 새 주소가 필요하면:** **배포 → 새 배포 → 유형 선택 → 웹 앱**을 선택하고 배포합니다. 별도 배포 ID와 웹 앱 URL이 만들어지므로 사이트의 `endpoint`도 새 URL로 바꿔야 합니다.
   - 두 경우 모두 **실행 사용자: 나**, **액세스 권한: 모든 사용자**를 확인합니다. Sheet 자체는 비공개로 유지하며 웹앱이 배포자의 권한으로 Sheet를 읽습니다. [Google 웹앱 권한 안내](https://developers.google.com/apps-script/guides/web)
7. 배포 완료 화면 또는 **배포 관리**에서 **웹 앱 URL**을 복사해 현재 프로젝트의 `endpoint`와 비교합니다. `/exec`까지 포함한 전체 주소를 사용하고 주소 뒤에 동·호·닉네임이나 코드를 붙이지 않습니다. 배포 ID만 복사하지 마세요. 기존 배포 수정으로 주소가 같으면 JSON 변경은 필요 없습니다.

### 3. 프로젝트 URL 연결과 Pages 반영

8. URL이 달라졌다면 운영자는 **새 `/exec` URL만** 에이전트에게 전달하거나 프로젝트에서 직접 수정합니다. 실제 회원 코드·운영자 코드, Sheet 링크나 명단은 전달할 필요가 없습니다. `public/config/household-verification.v1.json`에서 `endpoint` 값만 바꾸고 `schemaVersion`, `enabled`, `provider`, `timeoutMs`는 유지합니다.

```json
{
  "schemaVersion": 1,
  "enabled": true,
  "provider": "google-apps-script",
  "endpoint": "https://script.google.com/macros/s/여기에_배포별_식별자/exec",
  "timeoutMs": 8000
}
```

위 주소는 **형식 예시일 뿐 실제 주소가 아닙니다**. Google에서 복사한 URL 전체로 대체하세요. 주소는 클라이언트에 공개되므로 비밀로 취급하지 않지만, Sheet ID·회원 정보·코드·해시는 이 파일에 넣지 않습니다.

9. Google 웹앱이 새 버전으로 동작하는지 확인하고, 실제 회원 정보 대신 임시 행이나 합성 데이터를 사용해 인증 성공·실패와 공개 입장을 점검합니다. 임시 회원으로 실제 코드를 발급했다면 테스트 후 코드를 폐기하고 행을 정리합니다. 로컬에서는 필요한 관련 테스트와 `npm run build`, `npm run verify:dist`를 실행합니다. 커밋된 상태의 배포 전 미리보기는 운영자 가이드의 `npm run local:pages`를 이용할 수 있습니다.
10. 확인 후 변경분을 커밋해 `main`에 푸시하고 **GitHub Actions의 Pages 배포 성공**을 기다립니다. 공개 사이트에서 새 `endpoint`, 공개 입장과 인증 동작을 다시 확인하세요. 웹앱 주소 변경 없이 프런트 파일도 바뀌지 않았다면 URL 연결을 위한 별도 Pages 배포는 필요하지 않습니다.
11. 인증명단의 기존 **인증됨** 회원도 본인 확인 후 아래 메뉴에서 개인코드를 개별 발급·전달합니다. 승인만 되어 있고 코드가 없으면 회원 인증은 통과하지 않지만 공개 입장은 가능합니다. `memberCodeRevision: 1`이 없는 기존 일반 회원 세션은 재인증해야 하고, 기존 개정 2 운영자 코드 세션은 유지됩니다.

## 탭과 상태

| 탭 | 열 | 용도 |
| --- | --- | --- |
| 인증명단 | 동 / 타입 / 닉네임 / 상태 | 인증됨·운영자·중지 회원만 관리 |
| 인증명단 E열 | 회원코드 해시 | 메뉴에서 생성된 코드의 SHA-256 해시. 코드 원문은 보관하지 않음 |
| 인증명단 F열 | 회원코드 발급일 | 발급·재발급 성공 시 자동 기록 |
| 인증명단 G열 | 회원코드 폐기일 | 폐기 시 자동 기록, 새 코드 발급 시 비움 |
| 가입요청 | 요청ID / 요청일시 / 동 / 타입 / 닉네임 / 심사결정 / 처리결과 / 처리일시 | 대기·승인·반려 이력 |

가입요청 A:B·G:H는 자동 기록입니다. 필요하면 숨기고 C:F를 중심으로 보세요. 요청 원문·자동 열, 인증명단 상태와 E:G 코드 메타데이터는 시트 보호 기능으로 신뢰하는 운영자만 편집하도록 제한하세요. 해시 열도 공개하거나 배포하지 마세요. 드롭다운은 인증 보안 장치가 아닙니다.

E:G는 코드를 직접 입력하는 칸이 아닙니다. 시트의 회원 관리 메뉴가 자동으로 기록합니다. F·G의 시각은 끝에 `Z`가 붙는 **UTC ISO 형식**으로 저장되므로 한국 시간은 9시간을 더해 확인합니다.

### 일상 승인

1. 가입요청에서 동·타입·닉네임을 확인합니다.
2. F열 심사결정을 **승인**으로 바꿉니다.
3. G열에 **승인 완료**가 표시되는지 확인합니다. 인증명단에는 인증됨 회원이 중복 없이 추가됩니다.
4. 실패 표시가 나오면 원문/기존 회원 상태를 정리하고 **미처리 승인 / 반려 재처리**를 실행합니다.
5. 본인 확인 후 인증명단에서 해당 회원의 개인코드를 발급하고 1:1로 전달합니다. **승인 완료만으로 개인코드가 생성되지는 않습니다.**
6. 사용자에게 선택 세대 요약 오른쪽의 **인증**과 전달받은 개인코드로 다시 인증하도록 안내합니다. 공개 입장은 닉네임을 2글자 이상 입력하면 가능하며 회원 인증과 별개입니다.

승인 성공 후에는 요청 행을 삭제하지 말고 필터로 감춰 이력을 보관하세요. 승인 완료 행의 결정을 바꿔도 회원을 삭제하지 않으며 승인으로 복원됩니다. 회원을 중지하려면 인증명단의 상태를 중지로 바꿉니다.

반려된 요청은 재신청해도 자동 승인/대기로 바뀌지 않습니다. 재심사할 때 운영자가 F열을 대기 또는 승인으로 바꾸세요. 승인으로 운영자를 새로 만들거나 중지 회원을 복구할 수는 없습니다.

### 회원 개인코드 발급·재발급

1. 코드 수령자의 본인 여부와 등록 정보를 먼저 확인합니다. **인증명단**에서 상태가 **인증됨**인 해당 회원의 **한 행**만 선택합니다. 헤더·여러 행·운영자·중지 행은 발급 대상이 아닙니다.
2. **분퍼빌 회원 관리 → 선택 회원 코드 발급/재발급**을 누릅니다. 열리는 모달에서 대상 회원을 다시 확인하고 **새 코드 발급**을 누릅니다.
3. 브라우저의 Web Crypto가 무작위 32바이트를 생성해 **43자의 base64url 코드**로 만듭니다. 서버가 대상 행·회원 정보·상태와 발급 작업의 유효시간을 다시 확인하고 SHA-256 해시를 저장합니다. 선택 행이나 회원 정보가 바뀌었거나 작업이 만료되면 모달을 다시 여세요.
4. **해시 저장 성공 뒤에만** 원문 코드가 한 번 표시되어 복사할 수 있습니다. 코드 원문은 인증명단·가입요청·Script Properties·로그에 보관하지 않습니다. 모달을 닫으면 원문을 다시 조회할 수 없으므로 전달 전에 복사하고, 잃어버렸다면 재발급하세요.
5. 확인한 본인에게만 신뢰할 수 있는 **1:1 경로로 개별 전달**합니다. 공용 채팅방·시트 셀·GitHub·공유 링크에 원문을 적지 말고, 화면 공유·주변 노출·스크린샷에도 주의하세요.
6. Web Crypto를 사용할 수 없다는 오류가 나온 경우에만 모달의 수동 입력 대안을 사용합니다. 비밀번호 관리자로 **16~128자의 무작위 코드**를 만든 뒤 입력하며, 저장 성공을 확인한 후 동일하게 개별 전달합니다.

**온라인 등록 요청이나 승인만으로 코드를 발급하지 않습니다.** 승인 후 운영자가 본인 확인과 위 발급 절차를 따로 진행해야 합니다. 회원에게도 코드를 다른 사람에게 전달하지 않도록 안내하세요.

같은 메뉴로 재발급하면 이전 코드는 새 인증에 사용할 수 없습니다. 분실·유출이 의심되면 본인 확인 후 재발급하고, 새 코드만 개별 전달하세요. 이미 열린 탭의 권한은 즉시 회수되지 않을 수 있습니다.

개인코드는 정규화한 동·타입·닉네임에 묶입니다. 실제 회원 정보를 변경하거나 다른 행으로 해시를 복사하면 기존 코드로 인증되지 않으므로 해당 회원에게 새 코드를 발급하세요. 수동 입력 대안에서도 다른 회원이나 기존 코드와 같은 값을 재사용하지 마세요.

### 회원 개인코드 폐기

인증명단의 **인증됨 회원 한 행**을 선택하고 **분퍼빌 회원 관리 → 선택 회원 코드 폐기**를 실행한 뒤 확인합니다. 메뉴가 E열 해시를 지우고 F열의 마지막 발급일은 유지하며 G열에 폐기 시각을 기록합니다. 재발급하면 E·F가 갱신되고 G는 다시 비워집니다. 직접 해시나 날짜를 입력할 필요가 없습니다.

폐기된 코드는 일반·공유 회원의 새 인증에 사용할 수 없습니다. 회원 상태 자체를 바꾸는 기능은 아니므로 공개 입장은 계속 가능하며, 회원 기능을 중지하려면 상태도 **중지**로 관리하세요. 복구할 때는 기존 원문을 조회하는 대신 새 코드를 발급합니다.

### 운영자

- 인증명단 상태가 운영자이며 **별도 코드가 일치**해야 모든 동·타입에 접근합니다.
- 닉네임만 아는 사람에게 운영자 역할을 주지 않습니다. 등록 요청도 운영자 행을 새로 만들지 않습니다.
- 코드는 사이트의 비밀번호 입력으로 POST 전송하며 브라우저 저장소·공유 URL에 넣지 않습니다.
- 코드 미설정은 실패 처리합니다. 잘못된 코드 6회 후에는 해당 닉네임의 추가 시도를 약 10분 제한합니다.
- 이는 단순한 추가 확인이며 정적 사이트 UI 권한입니다. 브라우저의 역할 값을 개발자 도구로 조작하는 것까지 막는 서버 접근통제는 아닙니다. 민감한 데이터·원격 관리 기능을 붙일 때는 Google 로그인 등 서버 검증 방식이 필요합니다.

### 공유와 개인 놀이터

- 개인 놀이터 회원 기능: 동 + 타입 + 닉네임 + 인증됨 상태 + 회원 개인코드가 필요합니다. 미등록·코드 없음·인증 실패 시에도 공개 기능으로 입장할 수 있습니다.
- 공유 놀이터: **보는 사람**의 동 + 닉네임 + 회원 개인코드로 승인 회원 여부를 검사할 수 있습니다. 공유자의 타입은 인증 조건이 아니며, 개인코드 없는 공개 권한만으로도 읽기 전용 열람이 가능합니다.
- 공유 인증으로 얻은 일반 회원 세션은 공유 열람용입니다. 개인 놀이터에 진입하려면 본인 세대를 선택해 다시 인증합니다.
- 공유 화면은 운영자에게도 읽기 전용입니다.
- 공유 화면에서 새 등록을 받을 때 공유자의 타입으로 잘못 등록하지 않도록 본인 세대 선택 화면으로 안내합니다.
- 닉네임만 아는 사람의 회원 인증은 허용하지 않습니다. 다만 개인코드까지 전달되거나 유출되면 대리 입력을 구별할 수 없으므로 코드 전달 전에 본인 확인하고, 공유 채팅방에는 올리지 마세요.

## 한도·복구

- 회원은 전체 행을 읽습니다. 이전의 5,000행 이후 회원 누락은 없습니다.
- 요청은 최대 5,000행 보관, 대기 최대 300건입니다. 한도 도달 시 새 접수를 거부하고 안내합니다.
- 같은 동·타입·닉네임의 반복 신청은 기존 행을 사용합니다. 같은 닉네임의 새 요청은 1분 간격으로 제한합니다.
- CacheService 제한은 남용 완화용이며 강한 봇 차단은 아닙니다. 심한 트래픽에는 별도 서비스가 필요합니다.
- = 등으로 시작하는 닉네임은 수식이 아닌 텍스트로 저장합니다.
- 상태 중지와 코드 재발급·폐기는 **새 인증부터** 반영됩니다. 이미 열린 탭은 서버에 권한을 계속 재검증하지 않으므로 탭 종료/세대 다시 선택 전까지 인증이 남을 수 있습니다. **이미 열린 모든 탭의 권한을 즉시 원격 취소하는 기능은 아닙니다.**
- 설치형 트리거는 설치 계정 권한으로 동작합니다. 스크립트/API로 값을 바꾸면 편집 트리거가 실행되지 않으므로 일괄 작업 뒤 재처리 메뉴를 실행하세요.
- 자동 백업 탭은 직접 삭제하지 않는 한 복구용으로 남습니다. 실패한 이동은 백업과 목적지 요청 행을 확인한 후 재실행하세요.

## 공개 설정

설정 파일에는 Google 웹앱 /exec 주소만 둡니다. Spreadsheet ID, 회원 명단, 회원·운영자 코드 원문과 해시는 저장소에 넣지 마세요.

- [Google 웹앱 배포](https://developers.google.com/apps-script/guides/web)
- [설치형 편집 트리거](https://developers.google.com/apps-script/guides/triggers/installable)

## 다음 개정 때 확인할 순서

1. 스프레드시트를 복사해 백업하고 `backend/apps-script/Code.gs`를 수정합니다.
2. 열 이름·상태·요청 action을 바꿨다면 Apps Script뿐 아니라 프런트 인증 클라이언트, mock, 계약 테스트와 이 문서를 함께 수정합니다.
3. 실제 명단 대신 임시 행으로 등록 요청, 승인, 개인코드 발급·재발급·폐기, 일반 인증, 운영자 인증, 공유 인증을 확인합니다.
4. **Apps Script 기존 배포를 새 버전으로 먼저 갱신**합니다. `/exec` 주소가 바뀐 경우에만 `public/config/household-verification.v1.json`을 수정합니다.
5. `npm run local:check`와 `npm run local:pages`로 Pages 배포 전 상태를 확인합니다.
6. Google 쪽 새 응답 계약이 정상임을 확인한 뒤 Bunfirvil `main`을 push하고 Pages 완료를 확인합니다.

이 순서를 지키면 구형 Apps Script와 새 프런트가 잠시 섞여 운영자 권한이나 공유 인증이 잘못 판정되는 시간을 피할 수 있습니다.
