# 인증·회원 운영 개정판

이 코드는 **같은 비공개 스프레드시트 안의 가입요청 / 인증명단 두 탭**을 사용합니다. 웹사이트는 명단을 내려받지 않습니다. 일반 회원 인증은 동·타입·닉네임을, 공유 열람 인증은 보는 사람의 동·닉네임을 확인합니다. 층·호수는 전송하지 않습니다.

## 현재 운영 계약

- `가입요청`은 신청·승인·반려 이력을 남기는 접수 탭입니다.
- `인증명단`은 실제 인증 판정에 사용하는 회원 탭입니다. 상태는 `인증됨 / 운영자 / 중지`만 사용합니다.
- 일반 회원은 동·타입·닉네임이 일치해야 하며, 운영자는 고유 닉네임과 별도 운영자 코드가 모두 맞아야 전역 접근합니다.
- 공유 열람은 보는 사람의 동·닉네임만 확인하고, 인증을 통과해도 공유 놀이터는 읽기 전용입니다.
- Spreadsheet ID, 실제 회원 데이터, 운영자 코드·해시는 저장소와 공개 설정에 넣지 않습니다.

## 기존 사이트 업데이트 순서 — 먼저 Google, 다음 Pages

프런트엔드 개정 2는 구형 서버의 닉네임 단독 운영자 인증을 거부합니다. **Google 웹앱부터 새 버전으로 배포한 후 GitHub Pages를 갱신하세요.** 순서가 바뀌면 운영자·공유 인증에 서비스 업데이트 안내가 나옵니다.

1. 기존 스프레드시트를 복사해 별도 백업합니다. 편집 권한은 신뢰하는 운영자에게만 줍니다.
2. Sheet의 **확장 프로그램 → Apps Script**에서 [Code.gs 전체 보기](https://github.com/is2js/naksaeng/blob/main/backend/apps-script/Code.gs) 전체를 교체하고 저장합니다.
3. 함수 선택에서 **setupVerificationSheet**를 한 번 실행하고 권한을 승인합니다.
   - 기존 인증명단 A:D와 회원 데이터를 유지합니다.
   - 가입요청 탭, 심사 드롭다운, 설치형 편집 트리거를 준비합니다.
   - 기존 다른 Script Properties는 지우지 않습니다.
   - 헤더가 다르면 덮어쓰지 않고 중단합니다. 구형 동/호수 명단은 백업 후 B열을 타입으로 직접 정리하세요.
4. **configureOperatorCode**를 실행합니다. Sheet에 나타나는 입력창에서 비밀번호 관리자로 만든 **16~128자의 무작위 코드**를 넣습니다.
   - 공개 닉네임과 다른 값이어야 합니다. 실제 코드를 채팅·GitHub·공개 설정 파일로 보내지 마세요.
   - 코드의 SHA-256 해시만 Script Properties에 저장합니다.
   - 이 프로젝트의 Sheet 운영자들은 같은 별도 코드를 사용합니다. Google 사용자별 로그인이 필요하면 별도 인증 시스템이 필요합니다.
5. Sheet를 새로고침하면 **분퍼빌 회원 관리** 메뉴가 나타납니다.
   - 기존 요청이 있다면 **기존 요청 분리 (백업 후 이동)**를 실행합니다.
   - 확인창 승인 후 인증백업-시각 탭을 만들고 요청 행만 가입요청으로 옮깁니다.
   - 인증됨·운영자·중지 행은 유지합니다. 요청 목적지 기록 후 원본 요청 행을 제거하므로 중간 실패 시 다시 실행할 수 있습니다.
6. **배포 → 배포 관리 → 기존 웹앱 수정 → 새 버전 → 배포**를 실행합니다.
   - 실행 사용자: 나 / 액세스 권한: 모든 사용자
   - 기존 배포를 수정하면 보통 기존 /exec 주소를 유지합니다. 주소가 바뀔 때만 public/config/household-verification.v1.json을 수정하세요.
7. 임시 회원 하나로 일반 인증, 다른 타입 공유 열람, 운영자 코드 없음/정상 코드, 등록→승인을 확인합니다. 테스트가 끝나면 임시 행을 제거합니다.
8. Google 배포 완료를 알린 뒤 프런트엔드를 Pages에 배포합니다. 구형 운영자 세션은 다시 인증해야 합니다.

## 탭과 상태

| 탭 | 열 | 용도 |
| --- | --- | --- |
| 인증명단 | 동 / 타입 / 닉네임 / 상태 | 인증됨·운영자·중지 회원만 관리 |
| 가입요청 | 요청ID / 요청일시 / 동 / 타입 / 닉네임 / 심사결정 / 처리결과 / 처리일시 | 대기·승인·반려 이력 |

가입요청 A:B·G:H는 자동 기록입니다. 필요하면 숨기고 C:F를 중심으로 보세요. 요청 원문·자동 열과 인증명단 권한 열은 시트 보호 기능으로 제한하는 것을 권장합니다. 드롭다운은 인증 보안 장치가 아닙니다.

### 일상 승인

1. 가입요청에서 동·타입·닉네임을 확인합니다.
2. F열 심사결정을 **승인**으로 바꿉니다.
3. G열에 **승인 완료**가 표시되는지 확인합니다. 인증명단에는 인증됨 회원이 중복 없이 추가됩니다.
4. 실패 표시가 나오면 원문/기존 회원 상태를 정리하고 **미처리 승인 / 반려 재처리**를 실행합니다.
5. 사용자에게 인증 확인을 다시 누르도록 안내합니다.

승인 성공 후에는 요청 행을 삭제하지 말고 필터로 감춰 이력을 보관하세요. 승인 완료 행의 결정을 바꿔도 회원을 삭제하지 않으며 승인으로 복원됩니다. 회원을 중지하려면 인증명단의 상태를 중지로 바꿉니다.

반려된 요청은 재신청해도 자동 승인/대기로 바뀌지 않습니다. 재심사할 때 운영자가 F열을 대기 또는 승인으로 바꾸세요. 승인으로 운영자를 새로 만들거나 중지 회원을 복구할 수는 없습니다.

### 운영자

- 인증명단 상태가 운영자이며 **별도 코드가 일치**해야 모든 동·타입에 접근합니다.
- 닉네임만 아는 사람에게 운영자 역할을 주지 않습니다. 등록 요청도 운영자 행을 새로 만들지 않습니다.
- 코드는 비밀번호 입력으로 POST 전송하며 브라우저 저장소·공유 URL에 넣지 않습니다.
- 코드 미설정은 실패 처리합니다. 잘못된 코드 6회 후에는 해당 닉네임의 추가 시도를 약 10분 제한합니다.
- 이는 단순한 추가 확인이며 정적 사이트 UI 권한입니다. 브라우저의 역할 값을 개발자 도구로 조작하는 것까지 막는 서버 접근통제는 아닙니다. 민감한 데이터·원격 관리 기능을 붙일 때는 Google 로그인 등 서버 검증 방식이 필요합니다.

### 공유와 개인 놀이터

- 개인 놀이터: 동 + 타입 + 닉네임 + 인증됨.
- 공유 놀이터: **보는 사람**의 동 + 닉네임으로 승인 회원 여부를 검사합니다. 공유자의 타입은 인증 조건이 아닙니다.
- 공유 인증으로 얻은 일반 회원 세션은 공유 열람용입니다. 개인 놀이터에 진입하려면 본인 세대를 선택해 다시 인증합니다.
- 공유 화면은 운영자에게도 읽기 전용입니다.
- 공유 화면에서 새 등록을 받을 때 공유자의 타입으로 잘못 등록하지 않도록 본인 세대 선택 화면으로 안내합니다.
- 일반 회원 인증은 여전히 닉네임을 아는 사람의 대리 입력까지 막지는 않습니다.

## 한도·복구

- 회원은 전체 행을 읽습니다. 이전의 5,000행 이후 회원 누락은 없습니다.
- 요청은 최대 5,000행 보관, 대기 최대 300건입니다. 한도 도달 시 새 접수를 거부하고 안내합니다.
- 같은 동·타입·닉네임의 반복 신청은 기존 행을 사용합니다. 같은 닉네임의 새 요청은 1분 간격으로 제한합니다.
- CacheService 제한은 남용 완화용이며 강한 봇 차단은 아닙니다. 심한 트래픽에는 별도 서비스가 필요합니다.
- = 등으로 시작하는 닉네임은 수식이 아닌 텍스트로 저장합니다.
- 상태 중지는 새 인증부터 반영됩니다. 이미 열린 탭은 탭 종료/세대 다시 선택 전까지 인증이 남을 수 있습니다.
- 설치형 트리거는 설치 계정 권한으로 동작합니다. 스크립트/API로 값을 바꾸면 편집 트리거가 실행되지 않으므로 일괄 작업 뒤 재처리 메뉴를 실행하세요.
- 자동 백업 탭은 직접 삭제하지 않는 한 복구용으로 남습니다. 실패한 이동은 백업과 목적지 요청 행을 확인한 후 재실행하세요.

## 공개 설정

설정 파일에는 Google 웹앱 /exec 주소만 둡니다. Spreadsheet ID, 회원 명단, 운영자 코드와 해시는 저장소에 넣지 마세요.

- [Google 웹앱 배포](https://developers.google.com/apps-script/guides/web)
- [설치형 편집 트리거](https://developers.google.com/apps-script/guides/triggers/installable)

## 다음 개정 때 확인할 순서

1. 스프레드시트를 복사해 백업하고 `backend/apps-script/Code.gs`를 수정합니다.
2. 열 이름·상태·요청 action을 바꿨다면 Apps Script뿐 아니라 프런트 인증 클라이언트, mock, 계약 테스트와 이 문서를 함께 수정합니다.
3. 실제 명단 대신 임시 행으로 등록 요청, 승인, 일반 인증, 운영자 인증, 공유 인증을 확인합니다.
4. **Apps Script 기존 배포를 새 버전으로 먼저 갱신**합니다. `/exec` 주소가 바뀐 경우에만 `public/config/household-verification.v1.json`을 수정합니다.
5. `npm run local:check`와 `npm run local:pages`로 Pages 배포 전 상태를 확인합니다.
6. Google 쪽 새 응답 계약이 정상임을 확인한 뒤 Bunfirvil `main`을 push하고 Pages 완료를 확인합니다.

이 순서를 지키면 구형 Apps Script와 새 프런트가 잠시 섞여 운영자 권한이나 공유 인증이 잘못 판정되는 시간을 피할 수 있습니다.
